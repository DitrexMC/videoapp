# ファイル機能仕様書

---

# 1. 概要

本機能は、ユーザーがファイルのアップロード・管理・共有・ダウンロードを行うための機能を提供する。

ファイルはフォルダとは独立した公開設定を持ち、アクセス制御は個別に行う。

---

# 2. 基本仕様

## 2.1 ファイル識別

* ファイルは一意のIDで管理する
* IDは推測困難なランダム文字列（UUID等）とする

---

## 2.2 ファイル情報

### 管理項目

* id
* upload_id
* folder_id（null許可）
* name（元ファイル名）
* safe_name（表示用に衝突解決済みの名前）
* size
* mime_type
* storage_path
* owner_user_id
* public（公開状態）
* status（uploading / processing / ready / expired / deleted）
* expires_at
* preview_status
* checksum
* created_at
* updated_at
* is_deleted

---

## 2.3 保存方式

* ファイル本体はストレージに保存する
* DBにはメタ情報のみ保存する
* ファイル名は保存時にUUID等へ変換する
* DBレコードは upload/init 時点で先行作成する
* 公開URLおよび内部参照は常に file_id ベースで扱う

---

# 3. アップロード仕様

## 3.1 単一アップロード

* ファイルはルート領域に保存される
* upload/init 完了時点で file_id を払い出す

---

## 3.2 複数アップロード

* 自動的に新規フォルダを作成し、その中に格納する
* フォルダ名は以下形式とする

```txt
フォルダ (n件)
```

### 補足

* 複数アップロード時に使用するフォルダモデルは別節の候補案から選択する

---

## 3.3 ファイル名重複

* 同一フォルダ内で重複を許可する
* 重複時は自動リネームを行う

### ルール

```txt
file.mp4
file (1).mp4
file (2).mp4
```

### 補足

* 元ファイル名は name に保持し、UI表示やZIP格納名には safe_name を使用する

---

# 4. アクセス制御

## 4.1 基本方針

* ファイルの公開設定はフォルダと独立する

---

## 4.2 公開状態

```txt
public = true  → 誰でもアクセス可能
public = false → 所有者のみアクセス可能
```

### 認証ヘッダ

* public = true の取得系APIでは Authorization ヘッダは任意
* public = false の取得系APIでは Authorization ヘッダ必須
* Authorization ヘッダが不要な場合、未送信または空文字を許容する

---

## 4.3 ダウンロード

* 必ずAPI経由で提供する
* storage_pathへの直接アクセスは禁止
* public = true の場合は認証なしダウンロードを許可する
* public = false の場合は所有者または管理者のみ許可する

---

## 4.4 フォルダ経由表示

* 非公開ファイルは以下の表示とする

  * 名前のみ表示
  * アクセス不可
  * サムネイルは鍵アイコン

---

# 5. ダウンロード仕様

## 5.1 単体ダウンロード

```http
GET /files/{id}/download
```

* アクセス権限を確認後、ファイルを返却する
* public = true なら未ログインアクセスを許可する
* public = false なら認証必須とする

---

## 5.2 複数ファイルZIPダウンロード

```http
POST /files/zip
```

### リクエスト

```json
{
  "file_ids": ["id1", "id2", "id3"]
}
```

---

## 5.3 処理仕様

* file_idsに対応するファイルを取得
* アクセス可能なファイルのみ対象とする
* 非公開または権限なしのファイルは除外する
* ready 以外のファイルは原則除外する

---

## 5.4 除外処理

### レスポンス

```json
{
  "included": 5,
  "excluded": 2
}
```

---

## 5.5 全除外時

* 対象ファイルが0件の場合、エラーとする

---

## 5.6 サイズ制限

* ZIP前の合計サイズが2GBを超える場合、処理を中断する

---

## 5.7 ファイル数制限

* 最大ファイル数制限を設ける（例：500件）

---

## 5.8 ZIP構造

* フラット構造とする

```txt
zip/
  file1.mp4
  file2.png
```

---

## 5.9 ファイル名衝突

### 対応

* 自動リネームを行う

```txt
file.txt
file (1).txt
```

---

# 6. フォルダ連携

## 6.1 フォルダZIP

* フォルダ内のfile_idを取得し、同一ZIP APIを使用する

---

## 6.2 表示制御

* フォルダは一覧表示のみ制御
* 実際のアクセスはファイル単位で判定する

---

## 6.3 フォルダ設計候補

### 案A: folder テーブルを持つ標準構成

* folder_id を主キーに持つ folders テーブルを作成する
* files.folder_id で紐づける
* owner_user_id、name、created_at、updated_at、is_deleted を folder 側で管理する
* 一覧、名称変更、削除、ZIP化、将来の階層化に最も拡張しやすい
* 現時点で最も推奨

### 案B: upload_batch テーブルをフォルダ代替として使う

* 複数アップロード単位の upload_batch を永続化し、files.batch_id で紐づける
* フォルダは UI 上のまとまりとして扱う
* 単純だが、後から手動フォルダや移動機能を追加しづらい

### 案C: フォルダを持たず、仮想グループ名のみ持つ

* files.group_label のような文字列だけを保持し、実テーブルを作らない
* もっとも実装が軽い
* rename、削除、権限継承、並び替え、将来拡張に弱い
* 最小構成としてのみ許容

### 共通要件

* どの案でも files は folder とは独立した public を保持する
* 同一表示グループ内の safe_name 重複解決ルールは必須
* フォルダZIPは最終的に file_id の集合へ変換して既存ZIP APIを使う

---

# 7. 削除仕様

## 7.1 ファイル削除

* 論理削除とする（is_deleted = true）
* status は deleted に遷移させる

---

## 7.2 物理削除

* 定期バッチにより完全削除を行う

---

# 8. セキュリティ

* ファイルは直接URLでアクセス不可
* 必ずAPI経由で提供する
* すべてのダウンロード処理で権限チェックを行う
* public = true の場合でも、削除済み・期限切れ・processing 中の非許可状態は遮断する

---

# 9. 制限事項

* 最大ZIPサイズ（合計2GB）
* 最大ファイル数制限あり

---
